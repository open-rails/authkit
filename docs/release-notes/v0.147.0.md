# v0.147.0: the #399 hard cut

Every host breaks. There are no aliases or shims; this table is the migration.

- One host type, `*authkit.Auth`, from the root package. Shared types live in
  `iam`; the engine is `internal/engine`, the HTTP layer `internal/httpapi`.
- Every mutation takes an `iam.Actor` right after `ctx`; reads take none. The
  zero actor is refused. Host code acts as `iam.OperatorActor()`; requests act
  as the actor `verify.ActorFromClaims` derives. See [roles](../roles.md).
- `authkit.New(ctx, cfg, deps)` takes a context: it creates the root group and
  reconciles the role catalog at boot.
- `Config.HTTP` is an `authkit.HTTPConfig` value; the zero value is headless.
- A permission group is an ID and a persona: no slug, display name or rename.
  Your app owns what a group guards (a channel and its name), stores the group
  ID, decides who may create or delete one, and calls `CreateGroup` /
  `DeleteGroup` with `iam.OperatorActor()`, optionally in its own transaction
  (`authkit.InTx(tx)`). See [roles](../roles.md#groups).

- A one-time link never answers `invalid_token`: a spent, expired or unknown
  verification, reset or passwordless link is `400 invalid_link`, a wrong code
  `401 invalid_code`. `invalid_token` is only for bearer and refresh tokens.
- A replayed SIWS message answers `challenge_not_found`.
- Deleted, nothing emits them: `email_unchanged`, `failed_to_request_phone_change`,
  `phone_unchanged`, `session_creation_failed`, `user_role_not_found`,
  `failed_to_update_preferred_language`, `not_group_member`, `token_revoked`,
  `email_not_verified`, `preferred_language_lookup_failed`, `failed_to_unban`.
- auth-ui: regenerate against `error-codes.ts`. `STALE_BEARER` is
  `token_expired`, `invalid_token`, `unauthenticated`, `unknown_kid`.

Other wire changes:

- API-key JSON `key_id` → `lookup_id`. `GET …/api-keys`, `…/invites/links` and
  `…/remote-applications` return `{object:"list", data, next_cursor}` and take
  `?cursor=&limit=`.
- Delegated tokens are refused on AuthKit's own management routes.
- Admin account routes (ban, unban, delete, restore, session revoke, root
  roles) authorize in the engine and accept user actors only.
- Group routes address groups by ID: `{api}/<persona>/{slug}/...` is
  `{api}/groups/{group_id}/...` (members, roles, API keys, remote applications,
  invite links), gated by the addressed group's persona. `POST {api}/<persona>`
  and the group's own `GET`/`PATCH`/`DELETE` are gone, as are the
  `group_create` and `group_settings` rate-limit buckets and the
  `X-AuthKit-Group-ID` / `X-AuthKit-Canonical-Instance` headers.
- Responses carry `group_id` and `persona`, never `instance_slug`
  (`/me/groups`, member and invite routes, 2FA role removal, application
  registration's `org`). `GET /me/permissions` takes `?group_id=` (default the
  root group) and answers `{object, group_id, permissions}`.
- Deleted error codes: `group_creation_refused`, `group_slug_invalid`,
  `group_slug_reserved`, `group_slug_taken`, `group_slug_application_managed`.
- Built-in permission names changed as in the table above; there is no `self`
  resource, and catalogs may use any resource name.
- `GET /me` drops `user_aliases`, `solana_address` and `discord_username`; read
  `solana_linked_account`.
- A service JWT's authority is its `permissions` claim; `scope` grants nothing.
- The `plan` claim is no longer read as `user_tier`.
- SIWS takes its domain from configuration only, never Origin or Host.
- Anonymous `POST /verify/request` answers `202` for every well-formed
  identifier; it no longer returns `user_not_found`, `email_already_verified`
  or `phone_already_verified`.
- New `passkey_required` (403): a non-passkey sign-in of an account that needs
  MFA, has a passkey and no factor.
- A device-key sign-in's `device_key` is the listing's shape: it adds
  `current: true` and, after a login, `last_used_at`.

## Behavior

- Machine actors (API keys, applications, delegated tokens) never issue API
  keys or invites. A user-issued credential dies with its creator's authority:
  demotion, ban, deletion or a role-catalog change revokes it, and every use
  re-checks the creator.
- `New` stores a role-catalog fingerprint; when it changes, `New` re-checks
  every credential, retiring what the new catalog no longer allows and logging
  it; that sweep never fails `New`. A catalog role shadowing a stored custom
  role fails `New`.
- `root:users:manage` always needs MFA, like `root:members:manage`. Only the
  operator sets another account's `Password` through `UpdateUser`.
- MFA follows permissions: API keys and applications never hold an MFA role.
- Checks are live for every actor. An unregistered permission makes `Can`
  return `iam.ErrUnknownPermission` and `RequirePermission` panic at build.
- Adding a member by email never binds an account; it invites (see Security).
  Bootstrap and `EnsureUserRole` never adopt an account by username, alias or
  unverified contact.
- `PurgeUsers` ends the recovery window by moving `purge_at` forward;
  `deleted_at` keeps the real deletion time.
- OIDC `redirect_uri` is the mount's `{oidc}/{provider}/callback`. Link and
  step-up starts under `/api/v1` used to name `/api/v1/oidc/...`, which was
  never served. `{api}/oidc/*` starts mount only with browser OIDC. Document
  resolvers fetch beneath the issuer's path.

## Security

Escalation audit 2 (N1–N10) and its leftovers:

- `POST /step-up/password` and provider step-up answer `step_up_required`
  (`mfa_required`) for an account with a second factor; its tokens' `auth_time`
  is the session's last second-factor proof, so a password re-auth never clears
  a sensitive gate. AuthKit's sensitive routes read live MFA state (N1).
- Device keys pass the session MFA gate: a key counts as a second factor only
  when enrolled with `code_2fa`; others are refused (`2fa_required`,
  `2fa_enrollment_required`) once the account needs MFA. A password change or
  reset revokes every other device key (N2).
- Machine actors cannot register remote applications. A group registration's
  registrar bounds its roles, and the credential sweep drops them when the
  registrar is demoted, banned or deleted (N3).
- The first proof of an address also revokes the squatter's invite links and
  account invitations and orphans its applications (N4).
- Signing in restores only a self-deleted account; staff deletions answer
  `account_disabled` and come back through `RestoreUsers` (N5).
- Self rules compare canonical (lower-case) ids (N6).
- `Verifier.Verify` refuses 2FA-enrollment tokens (and, under Required 2FA,
  unenrolled user tokens); `verify.ActorFromClaims` yields no actor for them (N7).
- The role-catalog fingerprint covers `RequireMFA` and the 2FA mode: keys and
  application roles that come to need MFA are revoked at boot and confer
  nothing at use (N8).
- Adding a member by email always answers `202` with an invitation, accepted by
  registering or by the account that verified the address at
  `POST /invites/redeem`; a failed verify link is always `400 invalid_link` (N9).
- A contact change never leaves an MFA-enrolled account unproven (N10).
- Bootstrap refuses MFA-required root roles for applications; `CreateGroup`
  refuses a banned, deleted or reserved owner; `MintAPIKey` refuses a persona
  without `APIKeys`, for the operator too.

Escalation audit 3 (P1–P7) and owner decisions:

- Device-key enrollment proves MFA only with a factor independent of the
  emailed code (TOTP, SMS, backup code), never the email factor (P1).
- The credential sweep retires an application owner role that confers nothing
  without the last-owner refusal, and the boot sweep never fails `New` (P2).
- An email factor is bound to the address it was proven for; an email change
  never redirects its codes (P3, N10).
- Group role operations and the sweep compare canonical subject ids (P4).
- A token claims `mfa` only as of its session's last MFA proof: a password
  step-up on a passkey session is fresh but not MFA (P5).
- A staff deletion of a self-deleted account is recorded; signing in no longer
  undoes it (P6).
- An account that needs MFA and has a passkey but no factor signs in with the
  passkey; a password answers `passkey_required`, never an enrollment token (P7).
- Anonymous `POST /verify/request` always answers `202` (owner decision a).
- `verify.Sensitive` reads `mfa_enrolled` from the token, at most one access
  TTL stale; AuthKit's own routes read live state (documented, decision b).
- `root:users:manage` needs MFA; only the operator sets another account's
  password (decision c).

Escalation audit 4 (R1–R5):

- **Upgrading:** the first boot retires every API key and application role
  that reaches `root:users:manage` (root admin or staff keys, bootstrap
  applications holding `admin`), because that permission now needs MFA;
  `ApplyBootstrapManifest` giving an application such a root role fails while
  2FA is on (I2).
- New operator-only `Auth.ResetAccountMFA` recovers a lost passkey or factor:
  it removes the account's passkeys, factors, backup codes, device keys and
  sessions and notifies it through the new `EmailSender.SendMFAReset` (R2).
- An application a departing user registered never replaces that user as
  owner: deleting or banning the last human owner answers `last_owner`. New
  `Auth.OwnerlessGroups` lists groups no owner counts for (R1, I1).
- The account's own confirmed email change moves its email factor to the new
  address. `GET /user/2fa` shows each email factor's address, and masked
  addresses read `a***@example.com` (R3).
- Device-key enrollment refuses a revoked or foreign key before asking for a
  second factor, and spends a backup code only when the key is enrolled (R4).
- `POST /register/resend` and `pending_registration_not_found` are removed;
  anonymous `POST /verify/request` resends a pending registration's code (R5).
- Migration `0009` pins each email factor to the account's address as it
  stood, including one staff set without proof before the upgrade (I3).
- Staff holding `root:users:manage` can still take over an account with no
  factor, including a passkey-only account under Optional 2FA, by moving its
  email and sending a reset (I4).
- Device-key enrollment on an email-only account with no backup codes left
  answers `2fa_enrollment_required`: enroll a TOTP or SMS factor (I5).

## Added

- Package `devicekey`: the Go client for device keys (`Client` with
  `BeginEnrollment`, `FinishEnrollment`, `Login`, `List`, `Revoke`,
  `RevokeOthers`), the signing domains and `SignEnrollment`/`SignLogin`
  ([device keys](../device-keys.md)).
- `iam.DecodeError(resp)` reads an AuthKit error response back into an
  `iam.Error` that `errors.Is` matches against the sentinels.
- `Auth.SessionEvents(ctx, userID, iam.SessionEventQuery)` pages an account's
  sign-in and session history. `GET {api}/admin/users/{user_id}/signins` is
  keyset-paged and returns `iam.SessionEvent` (`kind`, `ip`; no `user_id`).
- `Auth.ResolveUsername` resolves a name or live alias; `Auth.CheckUsername`
  checks availability for a new account without revealing who holds a name.
- `iam.ImportUser` gains `LastLogin`, `PreferredLanguage`, `AvatarURL`,
  `DeletedAt` (the 30-day lifecycle and its hooks run from it) and `Providers`
  (never an identity another account holds; wallets stay `ImportSolanaLinks`).
- `HTTPConfig.BasePath` roots the whole surface (API, browser OIDC, JWKS,
  documents) beneath the issuer's path, and `GET {api}/capabilities` reports
  the mount's `paths` ([mount layout](../api-endpoints.md#mount-layout)).
- `Deps.OnEvent` receives committed account and group changes (`iam.Event`:
  registration, contact and username changes, bans, deletion lifecycle, role
  and group changes) through River: recorded in the change's transaction,
  delivered at least once, ordered per subject, retried with backoff
  ([events](../events.md)).

`GroupUpdate`, `UpdateGroup`, `PurgeGroupOptions`, `GroupQuery.Search`,
`GroupCreation`, `Persona.Creation`, `Deps.InstanceAdmission`, the `self`
resource and `iam.PermSelf*`, `verify.Claims.PermissionGroupInstance`,
`PermissionScope.Instance`), `ReservedEscalationRole`,
`HTTPConfig.Documents`, `PerProcessRateLimits`, token role claims, the `plan`
and service-JWT `scope` fallbacks, SIWS Origin/Host domain fallback, the `/me`
duplicate fields, `GroupDirectory`, `WithResolvedGroup`, the compatibility
tooling (`compatibility/`, apidiff), and the public `dpop`, `password`,
`ratelimit` and `oidckit` packages.
