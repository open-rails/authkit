# Keys

AuthKit signs tokens with asymmetric keys and publishes their public halves at `/.well-known/jwks.json`. This page covers where the keys live and how to rotate them without a restart.

## The key directory

`Deps.KeySource` signs and publishes tokens. `keys.Watch(dir, logger)` serves a key directory's two files, `keys.json` and `totp.key`; keep both readable only by your server. A nil `KeySource` watches `/vault/auth`, except for a loopback issuer.

### Development keys

When `Config.Issuer` is on a loopback host (`localhost`, `127.0.0.0/8`, `[::1]`, the hosts where an http issuer is allowed) and `Deps.KeySource` is nil, AuthKit watches `$XDG_STATE_HOME/authkit/development/<issuer SHA-256>` (`~/.local/state/…` when XDG_STATE_HOME is unset; it must be absolute), so different issuers never share keys, and generates whichever of `keys.json` and `totp.key` is missing there, reusing them across restarts. No setting turns this on or off. Generation publishes each complete file atomically without replacing an existing one, so concurrent starters load the same keys. `New` logs one INFO line naming the directory whenever it signs with development keys.

AuthKit marks what it generates: `"development": true` in `keys.json`, and a `development:` prefix in `totp.key`. Any other issuer refuses to boot with a marked file ("development keys cannot sign for <issuer>: provision real keys"), so a directory first used locally never signs production tokens, and a hot reload never swaps development keys in for provisioned ones. Any other issuer also never generates: a missing `keys.json` fails `New`. Provisioned files, without the mark, serve any issuer. A `keys.Watch` source passed as `Deps.KeySource` is held to the same rule and generates nothing. Keys generated by releases before v1.54.0 carry no mark; delete them to have AuthKit generate marked ones.

`keys.json` holds the signing keys:

```json
{
  "active_key_id": "key-2026-06",
  "active_private_key_pem": "-----BEGIN PRIVATE KEY-----\n…",
  "public_keys": {
    "key-2026-03": "-----BEGIN PUBLIC KEY-----\n…"
  }
}
```

- The active key signs every new token, and its `kid` goes in the token header. RSA (2048–8192 bits) signs with RS256, P-256/384/521 with ES256/384/512, and Ed25519 with EdDSA.
- `public_keys` are verify-only keys that JWKS keeps publishing, so tokens signed before a rotation keep verifying. An entry under the active `kid` must be the active key's own public half, or the file is refused.
- `development` is `true` only in a file AuthKit generated for a loopback issuer; omit it in provisioned keys.
- With no `keys.json`, `New` fails, unless the issuer is loopback (development keys).
- A source with no active signer only verifies: AuthKit mints nothing (`iam.ErrSigningNotConfigured`), and JWKS serves the public keys alone.

`totp.key` is the AES key (16, 24 or 32 bytes; hex, base64 or raw) that encrypts authenticator-app secrets, served as `keys.TOTPSource` (`keys.Static` takes it as `TOTP`). It can't be rotated: replacing it breaks every enrolled authenticator app, so back it up. Without it, authenticator apps can't be enrolled, unless the issuer is loopback and AuthKit generates a development key.

Both files may be 0600, 0400 or 0440 (group-read, as a Kubernetes secret volume with `fsGroup` mounts them). World-read logs a warning; a group or world write bit refuses to boot. Both are read inside the key directory: a symlink that leaves it is refused.

To keep the private key out of the process entirely, set `Deps.KeySource` to your own `keys.Source`: an HSM, KMS or Vault key implements `keys.Signer`. Without `keys.TOTPSource`, TOTP is unavailable. A fixed source can't rotate without a restart.

## How rotation works

- **The issuer.** AuthKit reads `keys.json` through `keys.Watch`, which checks the file every 10 seconds and swaps in a changed one. A malformed, unreadable or group/world-writable file is logged and ignored; the last good keys stay. Minting and JWKS read the current keys on every call.
- **Verifiers.** A verifier that meets an unknown `kid` refetches the issuer's JWKS once, rate-limited, so other services pick up a new key when its first token arrives. This applies to issuers registered with a `JWKSURI`. Static `IssuerOptions.Keys` never refresh; call `AddIssuer` again with the new keys.
- **Delivery.** `keys.json` must be re-rendered in place while the server runs: a Vault Agent sidecar, or a Kubernetes Secret volume (which syncs within about a minute). An init container that renders the file once defeats hot reload.

Across replicas, a new key reaches each one within 10 seconds. In that window, a replica that hasn't reloaded yet rejects tokens signed with the new key. Clients retry, and the next poll closes the gap.

## Routine rotation

1. Generate a key pair with a new `kid`.
2. In the secret behind `keys.json`, make the new key active and move the old key's public half into `public_keys`.
3. Save. Within 10 seconds every replica signs with the new key, and tokens signed with the old one keep verifying.
4. Once every old token has expired (the access-token lifetime, 15 minutes; a day is a safe margin), remove the old key from `public_keys`.

## Emergency rotation

If a key may be compromised, do step 2 without keeping the old public key. Within 10 seconds AuthKit stops accepting tokens signed with it, and other verifiers stop when they next refetch: at the first token signed with the new key, and within 10 minutes. Users with those tokens sign in again, or refresh: refresh tokens are opaque and not signed.

## Authenticator app labels

Authenticator apps label an account with `Config.FrontendURL`'s hostname, such as `example.com`, the public sign-in hostname: Apple Passwords uses that domain to suggest matching saved credentials ([Apple's setup guidance](https://developer.apple.com/documentation/authenticationservices/securing-logins-with-icloud-keychain-verification-codes)). An IPv6 literal's colons become dots.

New provisioning QR codes include the matching issuer prefix and query parameter, the account's email (or username), SHA-1, six digits, and a 30-second period. This does not change existing factors or their secrets.

Scan the QR from inside the chosen authenticator app. Opening an `otpauth:`
link or scanning with a phone's Camera uses the operating system's registered
handler; the QR does not select Microsoft Authenticator or another app.
