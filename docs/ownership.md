# Ownership and role changes

Each group has at most one direct role per subject. Runtime replacement requires the actor to cover both the displaced and requested grants in the same transaction. Repeating an assignment still requires authorization but does not remove ownership. Revoking an absent role is a no-op after authorization.

An invitation is a bounded bearer grant: the offered role must cover the recipient's displaced grants, and cannot demote an owner. Only users and the operator issue invite links, account invitations and API keys. A user-issued credential never outlives its creator's authority: any change that leaves the creator unable to issue the credential's role (demotion, removal, a custom-role edit, MFA-role removal, a ban, deletion, a role-catalog change at boot) revokes it in the same transaction, and every use re-checks that the creator is live. Operator-issued credentials have no creator and are never swept. Revoking a key or link needs the authority to issue its role. Redemption binds the assignment to the authenticated recipient. Repeating a successful redemption for its existing role does not consume another use.

Owner-removing operations require another live, unbanned, unreserved user with the catalog `owner` role and enrollment satisfying the current global/owner MFA policy, or, where owners need no MFA, an enabled remote application with that role. An application a departing user registered never counts as that user's replacement, since its authority ends with theirs. Required-MFA eligibility follows the existing role-assignment enrollment rule: enabled MFA settings plus an enrolled factor. It does not infer enrollment from UV-only passkey login or probe sender health. Custom roles do not substitute for ownership. Add the replacement owner first; there is no unchecked recovery bypass. A live owner whose enrollment is still pending remains protected against removal unless a fully eligible replacement exists. Cleanup of an already banned, reserved, deleted or disabled principal does not create a new ownership loss. These checks describe stored eligibility, not external provider availability or possession of credentials.

New, never-owned groups may remain empty during bootstrap. Deleting a group intentionally ends its ownership obligation. `Auth.OwnerlessGroups` lists live groups no owner counts for: those created without one, and those the credential sweep at boot left without one (it logs a warning and never fails `New`).

Authority and account lifecycle mutations serialize with one transaction advisory lock per AuthKit schema, before group, account, MFA, or session row locks. These transactions explicitly use READ COMMITTED regardless of the host pool default, and evaluate temporary-ban expiry at the current statement time. This trades parallel administrative write throughput for a small consistent boundary across root grants, custom roles and account liveness. Ordinary authentication, reads and session issuance do not acquire it. Group deletion follows the same authority lock and then the group row lock. Applications removed by the deletion cascade must also leave usable owners in every surviving group they owned.

The engine's group store is a low-level SQL building block, not an actor-authorized host API. Hosts use `*authkit.Auth` operations. Code directly issuing SQL or store writes is responsible for its transaction and invariants; raw database access is outside the API's security boundary.
